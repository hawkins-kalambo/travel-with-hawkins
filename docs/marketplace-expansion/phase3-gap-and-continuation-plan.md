# Phase 3 gap audit & continuation plan

**Purpose:** reconcile the earlier engineering-baseline status report against the full approved Phase 3 product specification, with evidence gathered directly from the codebase rather than trusted from that report. This document is the source of truth going forward; the earlier report (19 Aug 2026) is superseded by it wherever the two disagree.

**Methodology:** three parallel, read-only research passes across the repository (branch `staging`), each auditing a subset of the specification's categories A–I against actual code, schema, and tests. No code was changed to produce this document. Every finding below cites the specific file, line range, migration, or table that is its evidence — "Implemented" is never asserted from a filename or variable name alone.

**Table format note:** the specification asked for twelve fields per requirement (Requirement / Purpose / Status / Evidence / Files / DB objects / Tests / Missing work / Business dependency / Risk / Acceptance criteria / Planned step). To keep ~90 requirement rows actually readable, *Files*, *DB objects*, and *Tests* are merged into one **Evidence** column below (each still cited explicitly); the other nine fields are kept as their own columns.

**Status labels used** (exactly as specified): `Implemented` · `Partially implemented` · `Not implemented` · `Deliberately deferred` · `Business dependency` · `Needs verification`.

**WhatsApp ownership boundary:** a separate, currently-uncommitted parallel effort owns `lib/whatsapp/`, `app/api/whatsapp/`, `app/api/admin/whatsapp/`, `app/admin/(sub)/communication/whatsapp-inbox.tsx`, `db/migrations/2026_08_10_whatsapp_customer_service.sql`, `docs/whatsapp/`, `tsconfig.whatsapp.json`. Every citation to those paths below is read-only research; nothing in this document proposes editing them. Confirmed via `git status --short` at audit time: all seven still show as untracked (`??`), unchanged by this session's own commits.

## Step 2 slice 3 completion record (S6: Content-Security-Policy)

A dedicated Explore pass audited every script/style/font/image/connect/frame/form-action source actually used in the app (not guessed) — confirmed via file:line evidence: no external scripts or analytics anywhere; the only inline script is a JSON-LD block (not JS execution); 8 inline `style={{}}` spots across 3 files (`app/global-error.tsx` — the root error boundary, deliberately self-contained — plus two dynamic-width progress bars); no external fonts; exactly the two `next.config.ts` image `remotePatterns`; Supabase REST/Realtime for `connect-src`; PayChangu confirmed to never be called from the browser (full-page redirect, ungoverned by CSP); one iframe (a Supabase Storage receipt URL). `next.config.ts`'s existing `headers()` (from slice 1) was extended with the policy rather than `proxy.ts`, since Next 16's `proxy.ts` (the renamed `middleware.ts`) has three separate response exit points that would each need the header repeated.

**A real bug was found and fixed during live verification, not before shipping.** The first version shipped `script-src 'self'` with no exception. A Playwright check against a real dev server (console-message + page-error capture across the homepage and five other pages) immediately caught 7 blocked "Executing inline script" violations on the homepage — Next.js's own framework runtime injects inline bootstrap/hydration scripts on every page, completely independent of any app code, and this would have broken the entire site. Per Next's own bundled CSP guide (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`), the alternative is a nonce-based policy — but that requires forcing every page into dynamic rendering (disabling static optimization/ISR site-wide), a far bigger architectural change than a bounded hardening slice should take on unilaterally. Fixed by adding `'unsafe-inline'` to `script-src` (matching Next's own documented "Without Nonces" fallback exactly), plus dev-only `'unsafe-eval'` (React's debug-mode eval usage, never present in production).

Re-verified after the fix: zero CSP violations across the homepage, `/trips`, `/customer/login`, `/admin/login`, `/payment/return` (the iframe page), and `/ambassador/settings/security` (one of the two inline-style-bar pages) — all loaded cleanly with the corrected policy. `npm run typecheck`/`lint`/`test` (186/186)/`build` all clean.

**Net effect on protection**: `'unsafe-inline'` on `script-src` reduces the policy's inline-XSS protection specifically — a real, honestly-stated compromise — but every other directive (`frame-ancestors 'none'`, `form-action 'self'`, `base-uri 'self'`, restricted `img-src`/`connect-src`/`frame-src`, `object-src 'none'`) still adds protection that didn't exist before this slice. A stricter nonce-based upgrade remains available later if the dynamic-rendering tradeoff is worth taking on.

**Explicitly deferred**: `report-uri`/`report-to` (would need a new endpoint to receive violation reports), a nonce-based script-src (the dynamic-rendering tradeoff above), refactoring the 3 inline-style files to remove `style-src 'unsafe-inline'` (`app/global-error.tsx` in particular shouldn't be touched — its self-containment is intentional).

**A real, pre-existing finding surfaced while scoping this**: running the exact command now in CI returns **8 high-severity vulnerabilities** as of 2026-08-20 — Next.js (cache confusion of response bodies, SSRF via rewrites with an attacker-controlled destination hostname, unbounded Server Action payload in Edge runtime, unauthenticated disclosure of internal Server Function endpoints, image-optimization DoS via SVGs), PostCSS (XSS via unescaped `</style>` in CSS stringify output, path traversal via `sourceMappingURL`), and sharp (inherited libvips CVEs) — all transitive through `next`. `npm audit fix --force`'s only proposed fix bumps `next` to `16.3.2`, itself flagged by npm as "outside the stated dependency range" — i.e. a major-version upgrade. **This is why the new CI step is report-only, not blocking**: making it blocking today would immediately redden every future push/PR for pre-existing debt nobody has reviewed, when the actual fix is a separate, real decision (upgrading Next.js in an app whose own `AGENTS.md` explicitly flags it as "NOT the Next.js you know").

Validated both new/changed YAML files parse correctly (`js-yaml`, inspected the resulting step list and ecosystem config directly) — no live GitHub Actions runner available locally to test against. `npm run typecheck`/`lint`/`test` (186/186)/`build` all clean (no app code touched).

An Explore pass enumerated all 87 `app/api/**/route.ts` files against `package.json`'s test list and found 69 completely untested. Picked the 5 highest-value, cheapest-to-test files — real, previously-unverified authorization logic, no new mocking infrastructure needed:
